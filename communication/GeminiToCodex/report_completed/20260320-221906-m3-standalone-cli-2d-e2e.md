## Summary
Investigated the E2E flow for creating and populating a 2D X-DOS disk using the standalone CLI. The flow successfully created the disk and copied the boot area, but failed during the `file cross-copy` step when attempting to transfer all files from `XDOS_SYS.D88`. The investigation identified that the destination 2D disk reached its physical capacity (80 clusters) because the current write implementation lacks cluster-sharing support for multiple small files. Furthermore, `XDosFatWriter` fails to bound cluster allocation to the physical disk limit, resulting in an out-of-bounds cluster assignment (Cluster 80 / C=40) and a subsequent `Sector not found` crash.

## Evidence
1. **First Failing Step**: `file cross-copy`
2. **Exact Error Text**: `Error: Failed to transfer file 'PALINIT': Sector not found: C=40, H=0, R=1`
3. **Failure Analysis**:
   - **Source Disk (XDOS_SYS.D88)**: Contains 74 files using 158 clusters worth of data via shared-cluster mapping (confirmed via `list` command and hexdump). Total capacity reported as 493 clusters due to an unbounded FAT.
   - **Destination Disk (XDOS_2D_STANDALONE_E2E.d88)**: Created as a standard 2D disk with 80 physical clusters (40 tracks * 2 heads).
   - **Allocation Failure**: The current `file cross-copy` implementation allocates a unique cluster for each file. After successfully copying 73 files and reaching Cluster 79 (Track 39 Head 1), it attempted to allocate a cluster for the 74th file (`PALINIT`).
   - **Root Cause**: `XDosFatWriter.AllocateClusters` lacks a bounds check against physical capacity (80 clusters for 2D). It erroneously returned Cluster 80, which maps to `C=40`. Since `C=40` is out of bounds for a 2D D88 image, `ReadSector`/`WriteSector` threw a "Sector not found" exception.
4. **Result Verification**:
   - `list images/test/XDOS_2D_STANDALONE_E2E.d88` confirms 73 files were successfully written, with the last file `TORGB` occupying Cluster 79.
   - File sizes for non-binary types (e.g., `After7`, `ﾏﾄﾞﾝﾅ`) on the source disk appear to use directory fields for other purposes (page counts), causing the current `FileSize` calculation logic to report smaller values or zero.

## Smallest Next-Fix Surface
1. **Immediate Crash Fix**: Modify `XDosFatWriter.AllocateClusters` to bound the allocation loop to the physical cluster count (80 for 2D, 160 for 2DD/2HD) derived from the disk's `DiskType`. This will cause the CLI to report `Disk full.` instead of crashing.
2. **Density Enhancement**: Implement shared-cluster support in the `WriteFile` path (respecting `FirstSectorR`) to allow high-density filesets like `XDOS_SYS.D88` to fit onto a standard 2D disk.

## Risks
- Without cluster-sharing, a bit-for-bit logical clone of `XDOS_SYS.D88` onto a 2D disk remains impossible for the full fileset.

## Requested Review
- Please review the failure analysis confirming the out-of-bounds allocation crash. Implementing the bounds check in `XDosFatWriter` is recommended as the next stability fix.
