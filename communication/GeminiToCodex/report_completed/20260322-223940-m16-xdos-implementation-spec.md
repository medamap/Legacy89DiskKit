## Provisional Conclusions
- Naive file copy is insufficient for 2D system disks due to strict 80-track capacity limits.
- Exact cloning of physical coordinates (`forcedStartTrack`, `forcedStartSectorR`) combined with raw block-copy of Track 0-2 is required for a viable duplication.

## Unknown
- General write-side shared-cluster semantic logic for new user files remains unknown.

## Explicit Ordered Implementation Sequence for C#
1. Introduce a dedicated `Duplicate` or `Clone` API at the filesystem or application layer that formalizes logical reconstruction.
2. Update the cloning write sequence to mask or ignore payload writes that overlap with reserved directory sectors (Track 1, R=2..10).
3. Utilize existing `forcedStartTrack` and `forcedClusterChain` APIs to extract and write each file strictly at its original physical coordinates.
4. Clone the raw FAT, FAM, and Directory sectors directly from the source image to the destination, overriding any intermediate state generated by the file writes.
5. Clone the boot tracks (Track 0) identically.

## Explicit Required Test Matrix
- **Unit Layer**: Test capacity boundaries and Track 1 sector masking.
- **Sample-Image Regression**: Logical duplication of `XDOS_SYS.D88` and `XDOSUTIL.D88` into new 2D images, followed by bit-for-bit extraction tests.
- **Standalone CLI E2E**: Verify CLI release tool detects, parses, and extracts files from the cloned image without error.
